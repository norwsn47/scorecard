## 8 September 2026 (magic-link hardening, #14/#15)

- **Per-email throttle and opportunistic cleanup on `POST /api/auth/request-link`.** Two auth-table housekeeping items done together on the one endpoint, no new infrastructure and no migration. **#14:** the endpoint now rejects with `429` when the address already has 5 or more unclaimed, still-fresh sign-in links (unused and issued in the last 15 minutes), so a target inbox can't be flooded with magic-link emails. `magic_tokens` has no `created_at` column, but every unused row's `expires_at` is exactly issued-time + 15 minutes, so `used = 0 AND expires_at > now` is an exact stand-in for "an unclaimed link issued in the last 15 minutes" — the check needs no schema change. Used tokens are excluded so signing in on several devices, or resending then clicking, doesn't count against the cap. Cloudflare's Workers Rate Limiting API and dashboard WAF rules were both considered and passed over: the API is a Workers feature with thin Pages support and only per-colo state, and a WAF rule would be dashboard-managed config outside the repo. A per-email D1 count is global, in-code, and reviewable. Per-IP limiting was not added — `magic_tokens` stores no IP and adding one cuts against the same data-minimisation goal as #15. A residual-abuse follow-up (Turnstile / WAF rule if abuse is ever observed; a real `created_at` column next time the schema is touched) is logged as BACKLOG #79. **#15:** the same call now also deletes any `magic_tokens` row whose expiry is more than 24 hours in the past (all such rows are long dead — 15-minute expiry, single-use). The prune runs after the response via `context.waitUntil()` with its failure swallowed, so a cleanup that fails (lock contention, a large first-run backlog) can never break sign-in — it is explicitly *not* coupled to the token insert. This stops email addresses from abandoned sign-in attempts accumulating in the table indefinitely (UK GDPR data-minimisation). A scheduled Worker was the other option but would be a separate deployment; opportunistic cleanup on the endpoint that creates the rows is enough at this scale. `PRD.md` §11.4, §11.12 and the `magic_tokens` schema note updated; new `functions/api/auth/request-link.test.js` covers both (429 over the limit with the query predicate asserted, allowed just under it, the deferred cleanup DELETE and its ~24h cutoff, a failed cleanup not failing the request, lowercase-normalisation, invalid-email rejection).

## 8 September 2026 (course edit and delete, #54/#71)

- **New course-edit screen, plus course deletion (cascading to its rounds).** Reached via a new "Edit" link next to the course selector in Setup. Lets a signed-in user rename a course and correct its per-hole par (`PATCH /api/courses/[id]`), or delete it entirely (`DELETE /api/courses/[id]`) — deleting cascades to every round recorded on that course, applied atomically via `DB.batch`, with a mandatory bottom-sheet warning stating exactly how many rounds will go ("This will also delete 12 rounds recorded on this course. This cannot be undone."). Deleting a user's default or only course is explicitly allowed (user's call) — the course selector degrades to an honest empty state ("No courses yet - add one to get started" + "+ New course") with no auto-promotion of another course to default, since silently picking one for the user would be more surprising than an empty state. `GET /api/courses` now also returns each course's `round_count` to drive that warning copy.
  Also new, and deliberately kept separate: a **"Par for this round"** section on the past-round edit screen (§11.13), letting a user fix the par recorded on one specific saved round without touching the course's own par definition — each saved round already stores its own `hole_pars` snapshot independent of the course, so this was a UI gap, not a backend one (`PATCH /api/games/[id]` already accepted `hole_pars`). Kept visually and textually distinct from the course selector above it per an explicit product decision, so the two are never confused. Two features considered and explicitly **not** built: an admin backfill route for pre-migration-003 courses (superseded by the real edit screen), and an "edit round total" control — the existing per-hole score edit is sufficient, since a round's total/winner/DNF is always derived live from hole scores (PRD §4.4), never stored as authoritative.
  The par-stepper grid used by course creation, course editing and round-par correction was extracted into a shared `ParStepperGrid` component so the three can't visually drift apart. `PRD.md` §6, §11.3, §11.7 and §11.13 updated to match. Two low-priority housekeeping items surfaced by code review and logged rather than fixed in this pass: a stale comment in `functions/api/courses/[id].js` describing a `user_id = null` "system default course" protection that no current seed path creates (#74), and `CourseEdit.jsx` not distinguishing an expired session from a genuine not-found (#75).
  **Follow-up, same day: a discoverable Quick Play for signed-in users with no course (#76).** User-flagged directly against the empty-course-selector state above: a signed-in user with zero courses could already start a round without one — `handleStart` never required a course selection, so tapping "Start the round" from the empty state silently produced a no-course, 36-hole, all-par-3 game (the same shape `createGame` already falls back to). The gap was purely that nothing said so — investigating turned up no missing capability, just an undiscoverable accident. Fixed by adding one line of copy to the empty state ("Or start below without one - Quick Play, 36 holes, all par 3.") rather than new logic or a new button, since "Start the round" already does the right thing. Confirmed via a live mocked run: zero courses → Setup renders the new copy → starting with just a player name lands cleanly on a 36-hole, all-par-3 Scorecard with no course title shown (Summary/History already hide a blank `courseName` gracefully via #69's optional-title handling). Deliberately **not** changed: `courseName` stays `null` for this path rather than being labelled "Quick Play" client-side, because a signed-in D1 round's course name is always re-derived server-side from `course_id` via a join — labelling it locally would only hold until the first reload from the database, after which it would silently revert to blank. Consistent blank beats a label that flickers away. Code review caught one edge case in the first version of this copy: the same empty-course-state block is also reachable while editing an existing no-course D1 round if the user's course list is currently empty - there the button reads "Edit hole scores" and the round keeps its own saved hole count/par, not a fresh 36-hole all-par-3 round, so the "Or start below..." copy would have described something that doesn't happen in that context. Fixed by scoping the new line to `!editRound` - it now only shows for a genuinely new round (New Game / Add Past Round), never mid-edit.

## 6 September 2026 (History back button, #72)

- **History's back button opened from the Bruntsfield page landed on the wrong screen.** User-reported: "Home button on History page not working." Root cause: `History.jsx` hardcoded `backLabel="← Home"` and called `goBack()` unconditionally, regardless of where History was actually opened from — History is reachable from both Home's and the Bruntsfield page's "Past Rounds" button (both signed-in only), but only the Home path was context-aware. Since `goBack()` steps through *real* browser history, opening History from Bruntsfield and tapping "← Home" actually landed back on Bruntsfield, not Home — the label lied about the destination. This is the same bug class #43b/#69 fixed for `Info.jsx`/`Rules.jsx`/`Setup.jsx`; `History.jsx` was simply missed. Fixed by mirroring the exact same pattern: `BruntsfiledCoursePage.jsx`'s "Past Rounds" button now passes `{ bruntsfield: true }`, and `History.jsx` uses that to show "← Course" (not "← Home") and `goBack('bruntsfield')` when opened from there. Also fixed the same narrow gap in `Setup.jsx`'s abandoned-edit-recovery redirect, caught by code review — it called `navigate('history')` without forwarding `bruntsfield` context, which would have reintroduced the same mislabel on that (rarer) path. Added a render test (`Setup.edit-recovery.test.jsx`) covering the context being forwarded correctly.

Also documented the previously-unspecced filter chips, standardised disabled-button opacity to `opacity-40` everywhere (Scorecard and Login previously used `opacity-60` / `opacity-50` with no stated reason), stated the outline-vs-fill selection-state split (segmented toggle vs filter chip) as a deliberate decision rather than an accident, and added a new `focus-visible` ring rule for every button — invisible on touch/mouse, giving keyboard/assistive-tech users a ring in the brand colour instead of the browser default. frontend-developer then implemented all of it: the two opacity fixes, History's "+ Add round" resized to the Header action tier spec, and the focus-visible ring added to 59 buttons across 11 files.
  - **Accent-token opacity-modifier bug (found during this pass, not part of the brief).** `--color-accent` was a hex string mapped via a plain `var()`, so Tailwind could not apply an opacity modifier to it — `ring-accent/40`, `bg-accent/10` etc. silently compiled to nothing at build time, no error. Fixed by converting `--color-accent` to RGB channels and remapping it through `rgb(var(--color-accent) / <alpha-value>)` — confirmed via the compiled CSS and Playwright screenshots that every affected utility now renders correctly, and that `accent` was the only token in the app ever used with an opacity modifier (nothing else needed the same fix).
  - **Deferred, not done in this pass:** three hand-rolled "back button" implementations outside `PageHeader` (Login's two screens, Summary's bespoke header) should compose the shared component rather than restyle it — flagged by design-director as a build note for next time, logged as a new backlog item rather than expanding this pass's scope.

## 3 September 2026

- **Score vs par — display standard + semantic colour (#38, #52, #64, PRD §5.3).** A single convention for how a score and its par render together, applied everywhere. **#38** — a live per-hole vs-par indicator: each scored cell shows a small superscript `+1` / `-1` / `E` trailing the stroke count, on the live Scorecard grid, the read-only Summary / History card, and the share image. **#52** — each player's round total now shows their score-to-par in brackets (`41 (+5)` / `38 (E)`) on the live totals bar, the Summary totals row, the "Finish Game?" dialog, and the share image. Both go through one shared `formatToPar()` helper (plus a new `roundToPar()`), and one shared `ParDelta` component in-app, so the notation can't drift between surfaces. **Colour (#64):** vs-par *deltas* now carry a semantic colour — under par `#2C6B3C` (a green kept clear of the brand accent so a birdie mark never reads as "winner"), over par `#9B3A24` (deep terracotta), level par uncoloured. This is a deliberate, tightly-fenced exception to the app's single-accent rule — deltas only, never chrome. **Override rule:** a delta keeps its semantic colour everywhere on the cream/card ground, *including* inside a winner's accent-green column; it drops to inverted white only inside the filled active cell. The §5.1 bracketed par *label* on the hole number is not a delta and stays uncoloured. New tokens in `src/styles/index.css` + `tailwind.config.js`, mirrored into the hand-drawn share canvas. One documented size exception: on the live totals bar the `(+5)` bracket is `text-sm` (not full size) so it doesn't wrap at 5–6 players on a 390px screen. Display only — no schema, migration or API change.
- **End-of-round tally vs par (#39) — built then removed the same day.** A per-player eagle/birdie/par/bogey count was added to the Summary, History detail and share image, then pulled on the user's call after seeing it in context: a solo round's tally is trivial and the block crowded the scorecard on a small screen. The round total-to-par bracket (#52) and the per-hole vs-par superscript (#38) cover the vs-par story. The `parTally()` helper and every tally surface were deleted; nothing of #39 remains.

- **Par UI rework + user course length, 9 or 18 holes (#48, #49, #50, #55).** A large change across the scorecard surfaces and course creation. **Par display** moved off the raised `(N)` superscript that #37 first shipped: each hole now renders as its number in **bold** followed by the hole's par in brackets — same font size, not bold, no colour of its own (e.g. **3** (3)). Identical on the live `Scorecard.jsx` grid and the read-only `Summary.jsx` table (both the post-finish view and the History detail view); the share image still shows no par and there is still no vs-par indicator (that's #38). **Course-creation par editor** rebuilt: the "set every hole to N" button row is gone (all-3s default unchanged), and the tap-to-cycle par grid is replaced by a two-column list of the course's holes, each row a `−  [par]  +` stepper clamped to a 2–7 band. **Course length:** course creation gains a 9 / 18 hole-count picker — default 9, fixed at creation (no course-edit flow yet — that's #54), 36 not offered for user-created courses. `POST /api/courses` now requires an explicit `holes` of exactly 9 or 18 (400 otherwise), validates `hole_pars` length against it, and returns `holes`. The **game model is hole-count aware** — `createGame` takes a `holeCount`, `buildEditGame` sizes the edit grid to the round's saved hole count so editing a completed 9/18-hole round no longer shows a trailing empty row — and `GET /api/games` joins `courses.holes` (as `course_holes`) so the edit grid can rebuild at the course's real length. `courses.holes`, previously stored and never read, is now load-bearing (it sets `hole_pars` length). **No new migration** — this relies on migrations `001` and `003`, both already live in production; only the value written to `courses.holes` and the validation around it changed. Quick-play Bruntsfield and the seeded default course for signed-in users are unchanged at 36 holes, par 3.
- **Fix — new game landed on the wrong hole (#47).** A live production regression: starting a new game, entering a past round, or creating a course then playing landed the focused scorecard cell on a stale hole (hole 3, or hole 7 after course creation) instead of hole 1. Cause: the active-cell position in localStorage (`gt_active_cell`) is a single global value cleared only when a round finishes, and `Scorecard` restored it unconditionally, so a cell left over from a previously abandoned game won over hole 1. Fix: `Setup.handleStart` now clears the active cell after saving a new working game (both the new-game/past-round and edit-round branches), and `Scorecard` only restores a persisted cell on a paramless mount (app reopen / Resume Game) — a game passed in via navigation params never inherits one. Resume-mid-game and restore-on-reopen (PRD §4.3) are unchanged. Follow-up logged to scope the active cell to a game id for robustness.

## 24 August 2026

- **Hotfix — duplicate game rows in D1 (Scorecard Plus).** Signed-in users saw duplicate rows for the same round. Two causes: (1) the summary screen re-POSTed on every "Done" tap with no idempotency protection, and after browser back/forward it fell back to the most recent local game and re-submitted it; (2) more significantly, the summary screen is reused for viewing any past round from History, and "Done" (its only way back) re-POSTed that round as a new row on every visit. Fixed in three layers: client stops re-saving an already-synced or History-opened round; every `POST /api/games` carries a `client_round_id` idempotency key (the local round's own id); server dedups on `(user_id, client_round_id)` with a `UNIQUE` index as a backstop (migration `002`). An earlier `(user_id, played_at, holes_played)` fallback match was removed after review flagged it could drop a genuine second same-day round. Pre-existing duplicate rows in production were left for a separate cleanup (BACKLOG). Round `notes` not pre-filling on the detail screen was fixed in the same pass.
